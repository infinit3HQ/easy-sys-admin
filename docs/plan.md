# easy-sys-admin: build plan

This expands the draft in `../PLAN.md`. The draft stays the source for the cleanup rules and the "rules with no switch". This file covers everything else: the web app, the server helper, all sysadmin features, the CLI, the MCP server, and the build order.

## 1. What we are building

One Go binary, `esa`, with these jobs:

| Command | Runs where | Purpose |
|---|---|---|
| `esa serve` | Control plane (Server_Media, one container) | Web UI, JSON API, MCP endpoint, scheduler, status poller |
| `esa helper <action>` | Each managed server, called over SSH with sudo | Does the work on the server: status, cleanups, upgrades, services, containers |
| `esa <subcommand>` | Your laptop | CLI client for the API |
| `esa mcp` | Your laptop, started by an AI client | Local stdio MCP server that forwards to the API with your token |
| `esa agent` | A managed server (optional, later) | Dials out to the control plane when inbound SSH is not possible |

```
            browser        esa CLI        AI agent (Claude, Kiro, ...)
               |              |              |            |
               | HTML         | JSON API     | stdio      | Streamable HTTP
               |              |          esa mcp ---------+
               v              v              v            v
        +-----------------------------------------------------+
        |  esa serve                                          |
        |   web  |  /api/v1  |  /mcp      <- three front doors |
        |   --------------------------------------------------|
        |   fleet service (permissions, rules, all reads/writes)
        |   poller | scheduler | runner | alerts | store (SQLite)
        +-----------------------------------------------------+
                 |  SSH: sudo esa helper <action> --json
                 v
             managed servers (esa helper binary + one sudoers line)
```

Two rules keep this simple:

1. Web handlers, API handlers, and MCP tools never touch the store or SSH directly. They all call the `fleet` service, which checks the caller's account and role. The three front doors cannot drift apart, and MCP cannot leak what the web page also cannot show.
2. Every command that runs on a server lives in the helper, in Go, with typed arguments. The control plane never builds a shell command from user input. The helper is also what the agent runs later, so SSH mode and agent mode share all server-side code.

## 2. Connecting servers

The draft said nothing gets installed on servers. With the full sysadmin scope that no longer works well: status, upgrades, and service control need root, and a pile of shell one-liners with sudo is hard to validate and easy to get wrong. So each server gets one static binary and one sudoers line. Nothing runs in the background on the server.

**Path A: enroll command (default).**

1. Each account has an Ed25519 keypair generated by the control plane. The private half is encrypted at rest and never leaves the process.
2. The add-server page shows one command to paste on the server:
   `curl -fsSL https://esa.example/enroll/<one-time-token> | sudo sh`
   It also shows the manual steps for people who will not pipe to sh.
3. The script creates a system user `esa`, installs the account's public key for it, downloads `esa` for the server's architecture to `/usr/local/lib/esa/esa`, and writes `/etc/sudoers.d/esa`:
   `esa ALL=(root) NOPASSWD: /usr/local/lib/esa/esa helper *`
   It prints the host key fingerprint.
4. The page tests the connection, shows the fingerprint, and you accept it. Later runs refuse to continue if that key changes. The token expires after 15 minutes or one use.

**Path B: give the control plane a sudo login once.** Enter a password or private key for a user with sudo. The control plane SSHs in, does the same install as the script, switches to the `esa` user and the account key, and deletes the password. You can tick "keep this login" but the UI marks that as the weaker option.

**Helper versions.** The control plane checks `esa helper version` on every poll. If it is older than the control plane, the server page shows "update helper", and that button uploads the new binary over SFTP.

**Path C: agent (later).** `esa agent` as a systemd service opens an outbound WebSocket to the control plane and runs the same helper actions locally. For servers behind NAT or without inbound SSH. The control plane stores no credential for those.

**SSH handling.** One SSH connection per server, reused across the poller and actions, with a fresh session per command. Keepalive every 30 seconds. Every command has a timeout. Host key checked on every connect.

Supported servers for v1: Debian and Ubuntu, amd64 and arm64. RHEL-family support (dnf) comes later.

## 3. Web app

Server-rendered Go templates with htmx for live updates, embedded in the binary. No separate frontend build. Charts use a small library (uPlot) served from the binary. If the dashboard outgrows this, the web layer can move to an SPA on top of the same `/api/v1`.

Sign-in uses Authentik as an OIDC provider. Authentik must let `/api`, `/mcp`, and `/enroll` through to the app, because the CLI, agents, and enroll script use tokens and cannot do a browser login. The app checks those tokens itself.

Roles per account: `viewer` reads everything except logs, `admin` can run actions, `owner` also manages members, credentials, and alert channels.

Pages:

| Page | Shows |
|---|---|
| Fleet overview | One row per server: status dot, group, CPU, memory, disk, load, uptime, pending updates, reboot needed, failed units, unhealthy containers, last seen. Worst first. Totals on top. |
| Server detail | Tabs: Status (charts for 24h / 7d / 30d), Updates, Services, Containers, Logs, Access, Security, Scheduled jobs, History |
| Group | Members, schedule, cleanup and update switches, run now, measure only |
| Run detail | Per-server steps, bytes freed, packages changed, stderr on failure, duration |
| Alerts | Firing and resolved alerts, rules, notification channels |
| Activity | Audit log: who did what, from web, CLI, or MCP |
| Settings | Account members, API tokens, MCP setup snippet, account public key |

## 4. Sysadmin features

All of these run through `esa helper`. Read actions are open to every role. Write actions need `admin`, ask for confirmation, and write to the audit log.

### 4.1 Live status

The poller runs `esa helper status --json` on every server every 60 seconds. The helper reads `/proc` and a few commands and returns:

- uptime, last boot, kernel, OS release
- CPU % (two `/proc/stat` samples one second apart), load 1/5/15
- memory and swap used
- disk and inode use per real mount (tmpfs and overlay skipped)
- network bytes in and out per interface
- time sync state
- reboot required (`/var/run/reboot-required`)
- failed systemd units
- container counts: running, exited, unhealthy, restarting
- Docker disk use: images, build cache, volumes

Pending updates are counted every 6 hours with `apt-get -s upgrade`, split into security and other.

A server turns "unreachable" after 3 missed polls. Raw samples are kept 48 hours, hourly averages 90 days.

### 4.2 Updates and upgrades

Per group, two switches with their own schedule: **security updates** and **all updates** (`apt-get upgrade`). Off by default. Manual "update now" on a server or group. `dist-upgrade` and release upgrades are not offered.

How an update runs on one server:

1. Pre-checks over SSH: free space on `/` and `/var`, no other apt process holding the dpkg lock, `dpkg --audit` clean, held packages listed. A failed check skips the server with a red row and the reason.
2. `esa helper upgrade start` launches the upgrade with `systemd-run --unit=esa-upgrade-<run-id>`. It runs as its own systemd job, so it keeps going if SSH drops.
3. The control plane follows the job's journal. If the connection drops, it reconnects, checks the host key again, and keeps reading.
4. The result is stored: packages changed, exit code, reboot required.

apt runs with `DEBIAN_FRONTEND=noninteractive`, `--force-confdef --force-confold` (keep your config files), and `NEEDRESTART_MODE=l` (list services, do not restart them).

Servers in a group update one at a time. The first failure stops the rest of the group. Each group has a package hold list. Because the upgrade no longer depends on the SSH session, `openssh-server` is not excluded by default.

### 4.3 Reboots

- Manual "reboot" button per server.
- Optional per group: "reboot if required" in a window you set, one server at a time. Off by default.
- After a reboot the control plane waits up to 10 minutes for SSH, then checks that every container with a restart policy is running again. Anything else is a red row.
- The server that hosts the control plane is marked. It is never rebooted by a schedule, and the manual button warns that the page will go away.

### 4.4 Services (systemd)

- List units with state, enabled, memory, and since when. Failed units at the top.
- Start, stop, restart, view logs.
- Protected units (sshd, docker, containerd, and the control plane's own service) cannot be stopped from the UI. Restart asks you to type the unit name.

### 4.5 Containers

- List with image, tag, status, health, restart count, uptime, ports, compose project.
- Logs tail, start, stop, restart.
- Image age check once a day: compare the local digest with the registry digest and show "update available".
- "Pull and recreate" per container, only for compose-managed containers, using the project's working directory from the compose labels. Never on a schedule.
- Protected containers (Traefik, Authentik, Portainer, CrowdSec by default, editable per server) need the container name typed to confirm any action.

### 4.6 Logs

- Journal per unit and per container, last N lines, filter by priority and text.
- Live follow over htmx/SSE later.
- Logs can contain secrets, so they need the `admin` role in the web app and the `logs:read` scope for API and MCP.

### 4.7 Access audit (read-only)

- Local users with a login shell, members of sudo and docker groups.
- `authorized_keys` fingerprints per user, with a flag when a key appears on servers where it should not.
- Last logins and failed SSH login counts for 24 hours.
- Flags for `PasswordAuthentication yes` and `PermitRootLogin yes` in sshd.

### 4.8 Security checks (read-only)

- Listening ports with the owning process.
- Firewall state (ufw or nftables).
- CrowdSec or fail2ban state if installed.
- unattended-upgrades enabled or not.
- Pending security updates and reboot required, from 4.1.

### 4.9 Scheduled jobs (read-only)

Cron entries for all users and systemd timers with last and next run. Failed timers are flagged.

### 4.10 TLS certificates

A list of hostnames per account. Checked daily from the control plane. Alert 14 days before expiry.

### 4.11 Alerts

Rules per account, with defaults:

| Rule | Default |
|---|---|
| Disk or inode use | above 85% |
| Memory | above 90% for 10 minutes |
| Unreachable | 3 missed polls |
| Failed systemd unit | any |
| Unhealthy or restarting container | 5 minutes |
| Reboot required | for more than 7 days |
| Certificate expiry | under 14 days |
| Run failed | any |

Channels: ntfy, email (SMTP), and webhook (Discord and Slack formats). One message when an alert fires and one when it resolves, no repeats in between.

### 4.12 Not in v1

- Saved scripts run on a group. Arbitrary root by design, so owner-only, off by default, full audit.
- Browser terminal. Use your own SSH client for now.
- RHEL-family servers.
- Backup management.

## 5. Cleanups

Each cleanup is one Go file in `internal/hostops/clean/`, running inside the helper:

```go
type Cleanup interface {
    ID() string                         // "buildcache", "vscode", "journal"
    Measure(ctx context.Context) (Usage, error)   // bytes it could free, read-only
    Apply(ctx context.Context) (Result, error)    // does the work, returns bytes freed
}
```

A cleanup run for one server: connect, verify host key, `esa helper clean --measure`, then `esa helper clean --apply buildcache,vscode`, write the result. Servers in a group clean in parallel (default 4 at a time, 10 minute timeout each).

- **Build cache:** skip the server if a build is running (active buildx builders or `docker build` / `buildctl` processes), else `docker builder prune -f`.
- **VS Code copies:** under `~/.vscode-server/bin/` and `~/.vscode-server/cli/servers/` for every home that has `.vscode-server`. Keep the newest copy and any copy a running process uses (checked through `/proc/*/exe` and `/proc/*/cwd`).
- **Journal cap:** `journalctl --vacuum-size=<group setting, default 200M>`.

Apt updates moved to section 4.2. The "rules with no switch" from the draft each get a test that fails if the helper ever issues the forbidden command.

## 6. Scheduler

- A ticker every minute finds due groups in each group's own timezone.
- A group is claimed with an update that only succeeds if no run is active, so two ticks cannot start the same run.
- After a restart, a run missed by less than an hour still starts. Older misses are recorded as "missed".

## 7. CLI

A thin client over `/api/v1`. It never SSHs to servers itself.

```
esa login https://esa.example           # browser device flow, or --token
esa servers list [--group prod] [--json]
esa servers show media-01
esa servers add media-02                # prints the enroll command
esa status                              # fleet overview table
esa groups run prod [--measure-only] [--wait]
esa updates run prod [--security] [--wait]
esa runs list [--failed]
esa runs show <run-id>
esa alerts list
esa mcp                                 # stdio MCP server
```

Table output by default, `--json` for scripts. Token in the OS keychain with a 0600 file fallback. Released with GoReleaser for macOS and Linux, amd64 and arm64, plus a Homebrew tap.

## 8. MCP server

Goal: an agent can answer "which servers are low on disk", "what failed last night", "which containers have image updates" without screen-scraping.

- **Remote:** Streamable HTTP at `/mcp` with a bearer token, built on the official Go SDK (`github.com/modelcontextprotocol/go-sdk`) in stateless mode, which the 2026-07-28 spec expects.
- **Local:** `esa mcp` over stdio, forwarding to the API with the CLI's token.

Read tools (`read` scope): `fleet_summary`, `list_servers`, `get_server_status`, `list_groups`, `list_runs`, `get_run`, `list_alerts`, `list_updates`, `list_services`, `list_containers`, `get_security_report`.

Log tool (`logs:read` scope): `get_logs(server, unit or container, lines <= 500)`.

Action tools come later behind their own scopes (`runs:trigger`, `actions`), default to measure-only or dry-run, and never include credentials, server add or remove, or member changes.

Every MCP call goes to the audit log with the token id. Tool output never contains credentials. Server output (stderr, logs) is returned as truncated data, and agents should treat it as untrusted text.

## 9. Data model (SQLite)

```
accounts            id, name
users               id, issuer, subject, email, name
memberships         account_id, user_id, role (owner | admin | viewer)
sessions            token_hash, user_id, account_id, expires_at
account_keys        account_id, public_key, private_key_enc
groups              id, account_id, name, timezone, cleanup and update settings
servers             id, account_id, group_id, name, host, port, username, transport, hosts_control_plane
credentials         server_id, kind, secret_enc
host_keys           server_id, fingerprint, accepted_by, accepted_at
enroll_tokens       token_hash, account_id, server_id, expires_at, used_at
metrics_raw         server_id, at, json            (48 hours)
metrics_hourly      server_id, hour, json          (90 days)
server_state        server_id, last_seen, status json (latest snapshot for the overview)
runs                id, group_id, kind (clean | update | reboot), trigger, started_at, finished_at, status
run_servers         run_id, server_id, status, detail json, error
alert_rules         id, account_id, kind, threshold, duration
alerts              id, rule_id, server_id, fired_at, resolved_at
notify_channels     id, account_id, kind, config_enc
cert_targets        id, account_id, hostname, expires_at, checked_at
api_tokens          id, user_id, account_id, name, scopes, token_hash, last_used_at, revoked_at
audit_log           id, account_id, actor, action, target, at
```

- Every query is filtered by `account_id` in the fleet service.
- Secrets use AES-256-GCM with `ESA_MASTER_KEY` from the container environment. Each secret stores a key id so the key can be rotated.
- Migrations are numbered SQL files embedded in the binary, applied at startup. A copy of the database (`VACUUM INTO`) is taken before any migration runs on an existing database.
- SQLite in WAL mode with immediate write transactions. Nightly backup of the volume.

## 11. Build order

Each phase ends with something usable on our five servers.

1. **Skeleton.** `esa serve`, SQLite with migrations, OIDC sign-in, accounts and sessions, empty fleet page, Dockerfile and compose file.
2. **Add server.** Account keypair, encrypted secrets, enroll script and token, path B install, `esa helper status`, host key prompt.
3. **Live status.** Poller, fleet overview with real numbers, server detail with charts, unreachable state.
4. **Alerts.** Rules, ntfy, email, webhook.
5. **API, CLI, MCP (read-only).** `/api/v1`, API tokens, `esa` CLI commands, `esa mcp`, `/mcp`.
6. **Groups and cleanups.** Group form, measure-only runs, then build cache, VS Code, and journal. Scheduler and run history.
7. **Updates and reboots.** Section 4.2 and 4.3.
8. **Services, containers, logs.** Section 4.4 to 4.6 with actions.
9. **Audits.** Access, security, scheduled jobs, certificates.
10. **Agent mode.**
11. **Later.** Section 4.12.

## 12. Tests that matter most

- Each "rule with no switch" from the draft: a helper test that fails if a forbidden command (`docker system prune`, `--volumes`, `image prune -a`, restarting Docker or edge containers) is ever issued.
- A changed host key aborts before any command runs.
- Credentials never appear in run rows, logs, API JSON, or MCP output, one test per front door.
- A token from account A gets nothing from account B through the API and MCP.
- Upgrade survives a dropped SSH connection (kill the connection mid-run, reconnect, read the result).
- Integration target: a throwaway Debian container with sshd and Docker-in-Docker.

## 13. Decisions

| Question | Decided |
|---|---|
| Transport | SSH plus the helper binary. Agent mode later. |
| Web stack | Go templates and htmx |
| MCP actions | Read-only first, actions later behind scopes |
| Metrics | Full status (section 4.1), not disk only |
| Passwords | Used once for setup and deleted, unless you choose to keep them |
| Other people's fleets | Accounts in the model now, no public sign-up yet |
| Distros | Debian and Ubuntu first |
