# Status

What exists, how it was checked, and what is left. Update this page when a feature lands or a known gap is closed.

## Built and verified

Checked against a real Ubuntu 24.04 arm64 server unless noted. Rocky Linux 9 package verification uses an isolated ARM64 container on the playground.

- Enrollment by pasted one-time command and by one-time sudo login. A reused command is refused. A changed host key pauses all work until someone accepts a matching fingerprint.

## Known gaps

- CLI commands for organizations, teams, and sharing. They are in the web app and the API only.
- On a run shared with another organization, the overall status can reflect servers that organization cannot see.
- A helper that speaks a protocol other than 1 is refused. The control plane sends an action only when the helper listed it, and the server page lists what a reinstall would add. A run whose servers lack an action it needs is refused with `helper_incompatible` before it starts. A stored capability list that is not valid JSON allows no action. Report revision 2 is required for a complete access or security report. An older helper is shown as not ready, and its last complete exposure summary is kept. SSH key fingerprints from a current helper are listed on the Keys page. The list is not every way to log in.
- A self-hosted install can re-seal stored secrets with `esa reseal` after setting `ESA_MASTER_KEY` to `<new>,<old>`. Remove the old key only when the command says the live rows use the current key. Backups taken before that still need the old key.
- Two control plane processes will not both start maintenance on the same server. The lock is a PostgreSQL advisory lock held for the run, and a second lock per run keeps a starting process from taking over a run another process still holds. Schedule slots, the Monday summary, and notification sends are claimed in the database. Which process polls is a lease: one process holds it for 70 seconds and renews it each cycle. Poll back-off is stored on the server row.
- A required reviewer on the GitHub `production` environment needs a paid plan while the repository is private.

## Outbound servers and Rocky support

- Outbound HTTPS polling, server-bound expiring credentials, recent-person registration and rotation, revocation, encrypted command/result queues, claim-once delivery, result receipts, and expired-task cleanup are implemented. The agent invokes only the installed typed helper. It refuses shell programs, internal upgrade execution, redirects, and self-uninstall. A reviewed explicit root installer and systemd service are included for amd64 and arm64. Outbound upgrades require durable helper idempotency. See [outbound-agent.md](outbound-agent.md).
- Rocky Linux 9 has RPM inventory, RPM CycloneDX identities, fail-closed security metadata, architecture-specific approved updates, and reboot checks. A DNF transaction is resolved, checked, and committed in one process. Unapproved dependencies, erasures, kernel removal, system versionlocks, and untrusted signatures are refused. Other RHEL-family releases remain unsupported. An isolated container verifies package operations; a Rocky VM reboot and external production deployment are not claimed.

- Following logs live.
- A configurable poll interval (fixed at 1 minute).

## Capacity

Measured with `TestPollLoad` (`apps/esa/internal/fleet/poll_load_test.go`): in-process SSH servers that answer `status` after 1.2 seconds, like a real server, and 55 second cycles.

| Healthy servers |        Dead servers | Concurrency | Polled in one cycle | Cycle time |
| --------------: | ------------------: | ----------: | ------------------- | ---------: |
|             300 |                   0 |           8 | all 300             |     46.0 s |
|           1,000 |                   0 |           8 | 360                 |     55.0 s |
|           1,000 |                   0 |          64 | all 1,000           |     19.6 s |
|           1,000 | 50, before back-off |          64 | all 1,000           |     37.0 s |
|           1,000 |  50, after back-off |          64 | all 1,000           |     19.6 s |

Concurrency 64 is the default. Going by the 1,000-server result, one control plane should poll about 2,500 servers a minute at that setting (not measured beyond 1,000); raise `ESA_POLL_CONCURRENCY` for more. Poll back-off is stored on the server row, so a restart does not immediately retry a failing login. One process holds the poll for 70 seconds and renews it; another process skips that cycle. Action rate limits are one shared count in PostgreSQL. Password sign-in limits, sign-up attempts, and mail send counts are shared rows in PostgreSQL, so a second process does not get its own quota. A queued notification is a database row. The process that stored it tries to send at once; every process sends what is still queued, and the claim stops a second send. The board loads every server of a space every 15 seconds, which is fine at the default cap of 500 servers per space.

## Active worker ownership

Maintenance checks the original advisory-lock connections before every helper call in a run and every 5 seconds while waiting. Losing one cancels that worker. It leaves unfinished server rows for recovery and does not finish a run or advance its next batch. Reconnecting to PostgreSQL is not proof of ownership. Tests disconnect the worker after an install was sent and verify that the next batch stays queued, then that another worker follows the first install and starts only the remaining one.

Two-admin plans have a database guard as well as API checks. A proposal written by an older binary inherits the group's requirement. A single approval cannot move it to approved or executing. An older group update cannot turn off required plans while the two-admin requirement remains enabled. Tests exercise those older write shapes against the current schema. The executable matrix also starts baseline `b74e5f2` and the current binary against one database, testing proposals and refused single approvals through both versions. It is a supported baseline matrix, not every historical release.

## Operator-run reachability evidence

`esa servers probe` attempts a TCP connection from the operator's machine to the enrolled server host and submits typed evidence. The API checks owning-group admin access and the actions scope. Reads use server visibility. A view or operate share cannot submit evidence for its owner. The security tab and MCP expose the latest attempt and last complete observation. Missing, failed, stale, and reached are separate states. Reports older than the latest attempt cannot replace it. An enrolled address change invalidates previous evidence. The control plane does not probe external addresses or change a server. Each server has at most 128 source and port pairs; the CLI connection timeout is 5 seconds and evidence freshness is 15 minutes.

## Scanner and retention decisions

[scanner-comparison.md](scanner-comparison.md) records actual offline Grype 0.122.0 and Trivy 0.76.2 results on one synthetic SBOM. Grype remains the supported optional scanner. The tools and databases are not bundled or redistributed. Their software licences are Apache-2.0; operators supply their own scanner and feeds, whose terms still apply. Fewer matches are not evidence of better accuracy.

`ESA_REPORT_RETENTION` optionally prunes old resolved notices and superseded scans. The latest scan, unresolved notices, run reports, and backup receipts are kept. It defaults off. The audit hold also pauses report deletion. The published hosted policy uses these same settings; production deletion is enabled only by explicit deployment variables. See [configuration.md](configuration.md).

## Build channels

`main` is production; `nightly` is an isolated preview channel. CI validates the exact commit, publishes amd64/arm64 control-plane and web images to GHCR, then deploys their exact digests through the existing Server One runner. Nightly has independent secrets, restricted sign-in, its own database/networks/project, and bounded resource use. Pull requests never publish or deploy. The self-hosting guide covers source builds and published images. The daily nightly schedule activates when the workflow reaches the default branch. See [deployment.md](deployment.md).

The first hosted nightly CI run exposed two cases that local checks had missed. Approval timestamps now use PostgreSQL microsecond precision so the first and second approval return the same expiry on nanosecond clocks. Maintenance lock sessions use separate run/server pools, preserving query capacity on small hosts. A regression runs more maintenance work than the available two-connection pools and requires every run to finish.

Multi-platform web publication builds the portable JavaScript bundle on the builder CPU. This avoids an ARM64 Vite/Rolldown compile that stalled under QEMU; native addons in the server output fail the image build.
