# Status

What exists, how it was checked, and what is left. Update this page when a feature lands or a known gap is closed.

## Built and verified

Checked against a real Ubuntu 24.04 arm64 server unless noted.

- Enrollment by pasted one-time command and by one-time sudo login. A reused command is refused. A changed host key pauses all work until someone accepts a matching fingerprint.
- The hardened `esa` user: root-owned home, forced command on the key, sudo limited to the helper. Hostile commands through the forced command are refused.
- Live status every minute: CPU, memory, disks and inodes, load, network, time sync, reboot required, failed units, Docker. Hourly rollups; 48 hours raw, 90 days hourly by default (`ESA_METRICS_RAW_RETENTION`, `ESA_METRICS_HOURLY_RETENTION`).
- Polling at scale: 64 servers at once by default (`ESA_POLL_CONCURRENCY`), servers that stop answering polled every 5 minutes, a 5 second TCP connect timeout, and a warning when a cycle runs out of time. Measured with a load test against in-process SSH servers (`internal/fleet/poll_load_test.go`), not a real fleet.
- `GET /metrics` on the control plane in the Prometheus text format (tests).
- Updates: pending list with security detection, security-only or full upgrades with held packages. Update and reboot runs work in batches of a group-set size and stop after a set number of failed servers. An upgrade survives `kill -9` of the control plane, and a restarted control plane follows every upgrade of the batch in flight. A test covers the worker dying after the install has started: the next process reads the result and does not start a second install. A test also covers the worker dying before the install was sent: the next process starts it, instead of waiting for an upgrade that does not exist.
- Reboots: wait for a new boot time, then check that containers with a restart policy came back.
- Cleanups: Docker build cache (skipped during builds), old VS Code server copies, journal cap.
- Services, containers (including pulling and recreating one compose service), logs, access and security reports, scheduled jobs, image update checks.
- A short note on each server, kept in the control plane. A group lists where its servers differ on password login, root login, firewall, and sockets listening on all interfaces. The status tab estimates how soon the fullest disk fills. A Monday summary goes to the space's channels when there is something to report. It lists each open security notice once, with the repeated subject counted as the same notice. The board counts servers whose helper is too old for the exposure summary.

A check that cannot read sockets, or cannot read Docker's published ports, keeps the last good list and does not store that partial read as the baseline. A summary with no successful collection for 2 hours is marked stale on the board and in the API, so old evidence does not read as the current state. A port Docker publishes is not treated as covered by ufw, and that mark is used only when ufw is the firewall. The exposure alert is off until an admin enables it. An older helper is reported as not ready rather than clean. A new socket on all interfaces or on one public address, or a new SSH key on any login, sends one notice. While the notice is open, seeing it again sends nothing. A notice is open, reviewed (with an optional note), snoozed for up to 7 days, accepted as a risk for up to 90 days with a reason, or resolved. ## Known gaps

- CLI commands for organizations, teams, and sharing. They are in the web app and the API only.
- On a run shared with another organization, the overall status can reflect servers that organization cannot see.
- A helper that speaks a protocol other than 1 is refused. The control plane sends an action only when the helper listed it, and the server page lists what a reinstall would add. A run whose servers lack an action it needs is refused with `helper_incompatible` before it starts. A stored capability list that is not valid JSON allows no action. Report revision 2 is required for a complete access or security report. An older helper is shown as not ready, and its last complete exposure summary is kept. SSH key fingerprints from a current helper are listed on the Keys page. The list is not every way to log in.
- A self-hosted install can re-seal stored secrets with `esa reseal` after setting `ESA_MASTER_KEY` to `<new>,<old>`. Remove the old key only when the command says the live rows use the current key. Backups taken before that still need the old key.
- Two control plane processes will not both start maintenance on the same server. The lock is a PostgreSQL advisory lock held for the run, and a second lock per run keeps a starting process from taking over a run another process still holds. Schedule slots, the Monday summary, and notification sends are claimed in the database. Which process polls is a lease: one process holds it for 70 seconds and renews it each cycle. Poll back-off is stored on the server row.
- A required reviewer on the GitHub `production` environment needs a paid plan while the repository is private.

## Capacity

Measured with `TestPollLoad` (`apps/esa/internal/fleet/poll_load_test.go`): in-process SSH servers that answer `status` after 1.2 seconds, like a real server, and 55 second cycles.

| Healthy servers |        Dead servers | Concurrency | Polled in one cycle | Cycle time |
| --------------: | ------------------: | ----------: | ------------------- | ---------: |
|             300 |                   0 |           8 | all 300             |     46.0 s |
|           1,000 |                   0 |           8 | 360                 |     55.0 s |
|           1,000 |                   0 |          64 | all 1,000           |     19.6 s |
|           1,000 | 50, before back-off |          64 | all 1,000           |     37.0 s |
|           1,000 |  50, after back-off |          64 | all 1,000           |     19.6 s |

Concurrency 64 is the default. Going by the 1,000-server result, one control plane should poll about 2,500 servers a minute at that setting (not measured beyond 1,000); raise `ESA_POLL_CONCURRENCY` for more. Poll back-off is stored on the server row, so a restart does not immediately retry a failing login. One process holds the poll for 70 seconds and renews it; another process skips that cycle. Action rate limits are one shared count in PostgreSQL. Password sign-in limits, sign-up attempts, and mail send counts are shared rows in PostgreSQL, so a second process does not get its own quota. A queued notification is a database row. The process that stored it tries to send at once; every process sends what is still queued, and the claim stops a second send. The board loads every server of a space every 15 seconds, which is fine at the default cap of 500 servers per space.
